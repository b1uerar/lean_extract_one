# lean-extract
纯ai generated代码，只适合作为toy使用。


从一个 Lean 文件中提取指定定理及其本文件依赖，保留原陈述和原证明，输出新的 Lean 文件。首版已针对 Lean 4.26.0 编写，运行测试见下文。

当前适合常规数学文件的实验性提取及人工复核后的使用。已有标准库和 Mathlib 案例通过检查，但尚不能保证任意 Lean 文件的语义不变。两处已复现的验证漏洞暂未修复，`type verified` 只表示通过当前实现的检查，详见[已知限制](#已知限制)。

## 使用

需要 Python 3.10 或更新版本，以及 Lean 4.26.0。无需安装 Python 第三方包。

```bash
./lean-extract Input.lean --theorem MyNamespace.target --output Extracted.lean
```

指定 Lean 可执行文件和 Lake 项目：

```bash
./lean-extract /path/to/project/Example.lean \
  --theorem Example.target \
  --output /path/to/project/Extracted.lean \
  --lean /path/to/toolchain/bin/lean \
  --project /path/to/project
```

- `--theorem` 接受完整名称或无歧义的短名称，包括私有定理。名称歧义时列出候选。目标必须在输入文件内定义。
- `--lean` 指定 Lean 可执行文件。省略时在输入文件所属项目中解析默认 Lean 工具链。
- `--project` 指定含 `lakefile.toml` 或 `lakefile.lean` 的目录。省略时从输入文件向上寻找项目。
- `--output` 必填。输出目录须已存在。只有验证成功后才写入输出。
- `--force` 允许替换已有输出，但不允许覆盖输入或写入符号链接。

项目模式使用所选 Lean 自带的 Lake，通过 `lake setup-file` 获取模块选项、imports 构建产物及插件，并通过 `lake env` 获取搜索路径。Lake 可能编译尚未构建的 imports 或生成项目缓存。指定 Lean 必须与项目依赖兼容。没有 Lake 项目时使用所选 Lean 与当前 `LEAN_PATH`。

其他 Lean 版本会显示未经验证的提示。工具依赖 Lean 内部 API，因此不能保证任意版本兼容。

## 提取规则

1. 对整个输入文件执行 Lean 检查。允许原有 `sorry` 警告；任意位置出现错误都会终止。
2. 从目标的类型和证明出发，递归收集本文件常量依赖。外部声明只通过原 imports 提供，不展开源码。
3. 根据逐条命令处理后的环境，将常量映射回源码命令。保留命令时也补齐该命令生成的其他声明的依赖，包括构造器、投影和辅助定义。
4. 从这次运行的 `InfoTree` 收集已解析的常量引用、执行的 elaborator、宏展开及中间 tactic 赋值。按语法节点追踪本文件的 parser、语法类别和宏注册，不再按名称后缀匹配其他命名空间中的声明。`simp only [extraLemma]` 中的引理即使未参与重写，也可能在 elaboration 时被解析，因此仍须保留原证明需要的引用。
5. 分析输入时启用 `trace.Meta.Tactic.simp.rewrite`，读取 trace 消息中的结构化常量信息。某些 `rfl` 引理实际参与了简化，但不会留在最终证明项中；这些执行依赖也会保留。此步骤不解析打印后的名字，不改写源码，也不重新执行 tactic。
6. 从目标命令开始求依赖闭包。带属性的声明、实例、类、`deriving`、记号和宏不再无条件保留。单独的 `attribute`、`grind_pattern` 和 `export` 命令按其作用对象关联到使用者。`#check`、`#print` 等诊断及独立模块文档不会带入无关声明。
7. 根据命令执行前后的 scope 栈，保留依赖命令原有的 `namespace`、`section` 和配对 `end`，以及当时有效的上下文命令。无关作用域整体删除，不移动声明，不合并作用域；`mutual` 和 `... in ...` 等复合命令不拆分。
8. 按原文件的字节范围删除未选中的完整命令。保留语句顺序、imports、原证明、语句内注释及声明文档注释。命令之间连续的空行最多保留两行，包括删除命令后合并出的空行；保留命令内部及块注释内部的空行不变，沿用原来的 LF 或 CRLF 换行格式。空行整理在输出验证之前完成。
9. 在另一个 Lean 进程中检查唯一的输出候选。该进程沿用原项目配置，只加载原 imports，不导入原目标文件，也不启用提取器额外的 rewrite trace。只有编译、目标类型及陈述依赖的一致性、保留命令原文核对全部通过，才写入输出；检查范围和漏检情况见下文。

每次提取只分析原文件一次、检查输出一次。没有试删、候选搜索或编译失败后补回语句的循环。验证负责拒绝错误结果，不参与删除决策。无法通过检查时明确失败，不通过复制完整输入或改写证明来兜底。

执行信息仍有边界。Lean 没有提供任意 metaprogram 对环境和选项读取的完整记录；同一语法种类的多个宏候选也不总能从 `InfoTree` 区分。因此，同种语法的活动宏注册、所需作用域内的 `variable`、`open`、`set_option` 等上下文，以及属性撤销、初始化和未知环境修改仍保守保留。内部提取计划的 `conservativeCommands` 标记保守保留的上下文和环境修改。它们不能被宣称为已证实参与证明的声明，输出也不承诺全局最小化。输入主动关闭 rewrite trace 或自定义代码依赖诊断选项时，现有记录可能不足；最终验证既可能拒绝输出，也存在下文所述的漏检。

## 类型核对

核对目标定理的内部类型表达式及宇宙参数，并检查陈述直接或间接依赖的本文件声明。对于这些依赖，比较其类型，以及定义和 `opaque` 的定义体；不要求定理证明项完全一致。

比较时按原源码命令匹配本地声明，处理私有名称中的模块名变化，忽略绑定变量名称和表达式元数据。比较不依赖 pretty printer，也不会因为两个不同定义打印成同一个名称就认为类型一致。

这是保守的结构比较，并非任意两个 Lean 环境之间的定义等价判定。如果宏生成的名称无法唯一匹配，或重新处理产生了结构不同的类型，会报告失败。验证也会拒绝原先不含 `sorry` 的保留命令新产生 `sorry`，并逐条核对保留命令的原始字节内容。即使改写后的证明仍能通过 Lean，也不能通过原文核对。

## 已知限制

以下两处问题已通过合法 Lean 代码复现，目前暂未修复。反例是刻意构造的边界情况，但宏、elaborator 和环境查询本身都是 Lean 的正常功能。

| 问题 | 已复现的结果 | 当前检查为何漏检 |
| --- | --- | --- |
| 输入分析额外开启 rewrite trace，改变了自定义 elaborator 可观察的选项 | 正常输入的目标参数是 `Bool`，输出变成 `Nat`，仍报告 `type verified` | 输入证书来自开启 trace 后的执行，未必代表原配置下的类型；该反例同时依赖 trace 选项和模块名 |
| 环境读取依赖不完整，且证书只覆盖陈述依赖 | 删除被 `env.contains` 查询的声明后，仅供证明使用的定义从 `1` 变成 `2`，仍报告 `type verified` | 该定义不在陈述依赖证书中；目标类型和证明项本身也可能保持相同 |

原文逐字保留并不等于 elaboration 后的含义不变。需要严格语义保证或批量生成无需复核的数据时，不能只依赖当前成功提示，应另行核对原配置下的目标类型和证明相关定义。

普通注释也可能在相关声明被删除后留下。它们不影响 Lean 编译，但注释可能看起来在描述下一条保留声明，阅读输出时需留意。空行整理不会删除或重写这些注释。

## 示例与测试

```bash
./lean-extract tests/fixtures/Basic.lean \
  --theorem Example.target --output /tmp/ExtractedBasic.lean

python3 -m unittest discover -s tests -v
```

测试使用实际 Lean 进程，覆盖传递依赖、完整证明、`sorry`、变量与命名空间、记号和宏、属性与实例、私有声明、结构体、`opaque`、`mutual`、`where`、原文保留、错误输入、名称歧义、Lake 项目和类型变更拒绝。新增测试覆盖被证明项省略的 simp 引理、无关注册的删除、同名声明隔离、作用域删除、跨命名空间 export、属性撤销的控制流影响，以及等价证明改写的拒绝。可通过 `TEST_LEAN=/path/to/lean` 选择测试工具链。

## 实现文件

- `lean_extract.py`：命令行参数、工具链与项目环境、进程隔离及验证后写入。
- `LeanExtract.lean`：Lean frontend、常量依赖闭包、源码命令映射、切片和类型核对。
- `tests/`：端到端测试与示例输入。
